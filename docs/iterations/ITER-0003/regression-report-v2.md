## D9 verification section

1. **Smoke step-7 literal assertion** (`tests/smoke/stack_test.sh`, reminder block): the poll requires `count(*) … and not (state = 'suppressed' and suppression_reason = 'todo_completed')` = 0, waits until the due instant +3 s has actually passed (so a late delivery could not mask itself), then asserts exactly 2 delivery rows for the completed todo and that no message body in either address's dev outbox contains 冒烟抑制. This is precisely the D9-referenced wording in the implementation plan's Task 15 and supersedes the O2 "no row outside (scheduled, suppressed)" adaptation. `make smoke-test` exited 0, so the literal assertion held at this HEAD.
2. **Revoke-time implementation** (`reminder/application/command/revoke.go`): reason validated by `domain.NewSuppressionReason` before any store mutation; order is `RevokePlanned` → `PlannedJobIDs` → best-effort `Cancel` per job → `ScheduledForSuppression` → `MarkSuppressed`+`Update`. Cancels never skip suppression; store errors propagate so the caller transaction rolls back. The handler owns no transaction and joins the caller's ambient transaction, making the suppressions atomic with the todo transition (proven against real Postgres by `TestRevokeSuppressesScheduledDeliveriesOnComplete/OnDelete`).
3. **Scheduled rows only** (`postgres/deliveries.go ScheduledForSuppression`): `workspace_id = $1 and todo_id = $2 and todo_reminder_version <= $3 and state = 'scheduled'`, tx-aware via `ExecutorFromContextOr`. Scoping integration test proves sending rows, final rows, above-cutoff rows, and cross-workspace rows are never returned.
4. **Reason plumbing**: complete ⇒ `todo_completed`, delete ⇒ `todo_deleted`, update/reschedule ⇒ `version_stale`, crossing the seam as a plain string in `RevokeReminderRequest.Reason` and validated on the Reminder side; invalid reasons (`""`, `"bogus"`) are rejected before any mutation (test asserts 0 revokes/cancels/updates).
5. **Sending rows untouched / in-flight path**: command test asserts the seeded `sending` row keeps its state and gains no reason during revoke; the execution-time suppression test set (`TestSendReminderSuppressesOnExecutionTimeReread` etc.) remains the correctness boundary for jobs already in flight, matching the D9 wording and the dated §6.1 erratum.
